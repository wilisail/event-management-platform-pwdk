# Optional tooling reference

This is a learning reference for TemuEvent. The [Feature 2 completion plan](feature-2-completion-plan.md) is the delivery schedule. The November 2 Learning Map treated several of these tools as ways to understand the existing stack or try something separately. Add a tool to the project only when it solves a specific gap in the current flow.

## Day 6 learning plan — try Docker, runtime handling, async work and Redis

Use a small local exercise to see how Docker makes an app's runtime more reproducible across computers. Containerize the Erogine or TemuEvent learning API and, if practical, a local PostgreSQL database with Docker Compose. Run the same simple API/database check inside the containers and from the usual local setup; note what Docker standardizes and what still comes from environment variables, network/ports, volumes and the external Supabase/Vercel services.

Trace runtime handling separately: Node.js runs the backend process, Express receives/routes HTTP requests and applies error-handling middleware, and Vercel runs the deployed application functions. Axios is an HTTP client used by frontend code to call an API; it does not run or manage the server. Observe where an error is logged, what safe response reaches the caller, and how the service is restarted or invoked after deployment. A background job such as expiring reservations needs a scheduler or worker that actually runs; Redis alone does not provide that runtime.

Study JavaScript async behavior with one route that awaits database I/O and one intentionally slow CPU-bound task. Follow how the event loop can serve other requests while it waits for I/O, and how blocking synchronous or CPU-heavy work can delay every request in that Node.js process. Async/await makes asynchronous code easier to write; it does not by itself create a durable queue, schedule a future task, or make a database update safe from races.

### Realtime updates — optional purchase experience

A WebSocket keeps a connection open so the server can push updates to a page; Supabase Realtime provides managed WebSocket-based subscriptions to database changes. For this project, an optional prototype could update the visible ticket availability when another buyer reserves, completes, or releases tickets. First compare this with simpler polling; add realtime only if it improves the learning outcome and fits the time.

Treat the live count as a truthful display hint, never as a promise or the authority to buy. The purchase API must still make the atomic availability decision in PostgreSQL. Send only the minimum public availability data, protect private subscriptions with authorization/RLS, and refresh from the API/database after reconnect so the page can recover from missed messages. Vercel Functions now support WebSockets; review [Vercel WebSocket support](https://vercel.com/docs/functions/websockets) and [Supabase Realtime database subscriptions](https://supabase.com/docs/guides/realtime/subscribing-to-database-changes).

Live chat is out of scope for TemuEvent: it is not in the current platform and there is no plan to build it. Do not add chat requirements or infrastructure as part of this ticket-availability exercise.

Then sketch a queue-backed job for non-immediate work such as sending an order email or reconciling an uploaded payment receipt. Identify who enqueues it, which worker processes it, how retries/backoff and duplicate delivery are handled, and how failures are inspected. Compare a durable queue with an in-process timer: a timer can disappear when the process stops or redeploys. Do not move the authoritative order, payment, or stock decision into a queue; commit those state changes transactionally in PostgreSQL, then queue follow-up work.

### Prisma seed data, mocks and TDD — learning path

Use repeatable dummy data to make the application easy to explore. A Prisma seed script writes realistic but fake records into a dedicated local or non-production database—for example, events, ticket types, and purchases in Waiting for payment, Waiting for admin confirmation, Done, Expired, and Canceled states. Never seed real customer/payment data or run a learning seed against Production.

A Prisma mock replaces database calls with controlled in-memory responses for a unit test. Use it to check service decisions such as invalid input, an unavailable event, an ownership denial, or a database error without needing a running database. A mock does not prove that SQL, schema constraints, transactions, or concurrent reservations work against PostgreSQL.

Try TDD (test-driven development) on one small rule: write an example of the expected behavior first, run it and see it fail, implement the smallest change that makes it pass, then refactor while keeping it passing. For example, define what should happen when payment arrives after `expiresAt`, then implement the server-side decision. Use a mocked Prisma client for the isolated service rule; use a dedicated real PostgreSQL test database to check migrations, constraints, transactions, and two buyers competing for the last ticket. TDD is a way to build in short feedback loops, not a replacement for testing against the real database.

### Redis-backed queue and worker — optional exercise

Redis can store queue/job state, but Redis is not the worker. The API is the producer: after a successful database transaction, it enqueues a follow-up job in Redis. A separate Node.js worker process reads the job, performs work such as sending an order email, records success/failure, and applies bounded retries/backoff. Make the job idempotent so a retry or duplicate delivery cannot send repeated effects or alter order/stock state twice. Inspect how failed jobs are surfaced and how queue depth is observed.

For TemuEvent, this is a learning comparison only: Redis, a Redis-backed queue, and its worker are not currently confirmed as configured. PostgreSQL remains authoritative for orders, payments, and inventory; commit those changes first, then enqueue optional follow-up work. The worker must have an actual runtime/hosting mechanism of its own; cron can schedule a periodic task, but does not automatically become a continuously running queue worker.

### Cron runner — schedule recurring work

A cron runner is the scheduler that starts a task on a recurring schedule. For TemuEvent, the task could scan for payment windows that have expired, mark eligible purchases Expired, release their reserved ticket stock, and enqueue follow-up notifications. It could also process organizer actions past the three-day deadline.

Compare these possible schedulers without assuming either is already configured:

- Vercel Cron calls a deployed route on a schedule. Its jobs run on Production deployments, not Preview. Current Vercel documentation says Hobby supports only once-daily schedules (with up to an hour of timing variation); Pro and Enterprise support once-per-minute schedules. A once-daily Hobby job is too slow for promptly cleaning up a two-hour reservation, so verify plan limits before selecting it. Secure the route with a server-only `CRON_SECRET`.
- Supabase Cron uses Postgres `pg_cron`; a job can run SQL/database functions directly or make an HTTP request, and job runs can be inspected in the Supabase dashboard. Decide whether the expiry logic belongs in a database function or should call the application API; don't duplicate business rules in two places.

The scheduled cleanup is not the authority for the deadline. Store an `expiresAt` timestamp in PostgreSQL and have the payment/checkout API reject late actions by comparing it with server/database time. Make the scheduled update transactional, idempotent, and safe to rerun; handle batches, errors and logs. Review the official [Vercel Cron guide](https://vercel.com/docs/cron-jobs), [Vercel limits](https://vercel.com/docs/cron-jobs/usage-and-pricing), and [Supabase Cron guide](https://supabase.com/docs/guides/cron).

Treat Redis as an optional experiment. If time allows, cache a frequently read product-list response, compare a cache miss with a cache hit, then change a product and verify the cached result is invalidated or refreshed. PostgreSQL remains the source of truth, especially for stock and order reservations. Skip Redis if it would distract from understanding the core API/database flow.

### Refresh-token storage comparison

TemuEvent's current setup stores hashed refresh-token/session records in PostgreSQL; Redis is not configured as the session store. Trace the existing login → refresh/rotation → logout/revocation path and identify which record is checked when a refresh token is presented. Do not display or copy raw tokens.

As a comparison exercise only, sketch how Redis could store a session identifier or token hash with a TTL, how logout/revocation would remove or invalidate it, and what happens to active sessions if Redis is unavailable or its data is lost. Compare expiry, durability, revocation, and operational dependencies with the current PostgreSQL approach. Do not migrate auth or add Redis just for this exercise; PostgreSQL remains the current session authority.

### TablePlus database inspection

Optionally use TablePlus as a desktop SQL client to inspect the non-production PostgreSQL schema and session-related tables. TablePlus is a manual database viewer/query tool; it does not host the database or replace Prisma, which is the application's database access layer. Start with read-only access and inspect table/column names and sample non-sensitive rows; do not edit or delete records, expose token material, or save/share production connection credentials. If TablePlus is unavailable, the Supabase dashboard or Prisma Studio can demonstrate the same database concepts.

Keep these as learning exercises. Do not point a container at Production or put production credentials in its image. The goal is to understand the difference between local containers and the hosted Vercel + Supabase deployment, not to add Docker or Redis to the production architecture.

## Day 7 integration check — traffic spikes, expiry jobs and live updates

Use a ticket-launch scenario to discuss what happens when many buyers request a small inventory at once. A queue can smooth or defer background tasks such as emails, but it does not prevent overselling by itself. The stock reservation must be an atomic/transactional database operation with a clear conflict result; consider rate limits or a waiting room/backpressure, and record how a burst is observed. Make clear which work can wait and which request needs an immediate answer.

Trace one end-to-end journey through browser/client → deployed API/runtime → PostgreSQL/Supabase → response. Verify that both features use compatible identity, record/status rules and environment configuration. Exercise one success and one controlled failure; inspect the available logs. If a cache was added as a Day 6 experiment, confirm it cannot show stale price/stock data or bypass the database's authority.

If using the TDD exercise, carry its passing rule into a real-database integration check. Seed only non-production test records, verify the expiry and ownership cases, and use a controlled concurrent-reservation scenario to check the database prevents overselling; Prisma mocks alone cannot establish that result.

If the optional Redis queue exercise is built, verify that the API enqueues only after the database transaction commits, the separate worker processes the job, a simulated temporary failure retries safely, and a duplicate job does not create a duplicate effect. Stop/restart the worker and observe how pending jobs recover. Keep this separate from cron expiry processing and from Redis caching; none of these should replace the database's stock/payment authority.

For live ticket availability, compare polling, Server-Sent Events (SSE), and WebSockets (including Supabase Realtime) at a high level. If the optional realtime path is tried, simulate two buyers viewing the same limited inventory: when one reserves or releases a ticket, the other should receive an accurate availability update that helps them decide whether to continue checkout. Do not create fake scarcity, expose another buyer's details, or treat a pushed count as a reservation. Verify reconnect/resync behavior and ensure checkout rechecks inventory atomically in PostgreSQL. Live order progress can be considered similarly, with private, authorized updates only. Keep live chat explicitly out of scope; it is not part of the current platform or plan. Countdown and live-count displays are hints; the database deadline and stock decision remain authoritative.

Verify one scheduled expiry run using test records: an unexpired purchase remains unchanged, an expired unpaid purchase transitions once and releases its reservation once, and a paid/confirmed purchase is not expired. Check the job's authorization, logs, rerun behavior and recovery from a missed/failed invocation. If using Vercel Cron, confirm its Production-only behavior and plan schedule limit; if using Supabase Cron, inspect the recorded job run. Verify the database deadline rejects a late payment even if the cleanup job has not run yet. If no scheduler is configured, mark this behavior pending rather than treating the countdown or a local timer as proof it runs.

Verify the current refresh-token path end to end: confirm a valid refresh can renew a session, a rotated/revoked token is rejected, and logout invalidates the session according to the database record. If a Redis alternative was only sketched, record it as a comparison—not as deployed infrastructure. Use TablePlus or another read-only client only against non-production data to inspect resulting session state; do not copy token secrets into the note.

Confirm any scheduled expiry/notification worker has an actual execution mechanism in the integrated deployment, and document its owner and trigger. If no worker or queue is configured, mark that behavior as pending instead of treating the timer shown in the UI as proof it runs.
