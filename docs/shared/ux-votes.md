## 1. Login handoff / Login saat membeli

- **A — Suggested / Disarankan:** Browse and select tickets first; login/register when checkout needs an account, then resume the selection. / Lihat dan pilih tiket dulu; login/register saat checkout memerlukan akun, lalu kembali ke pilihan tiket.
- **B:** Login before ticket selection. / Login sebelum memilih tiket.

**Why/impact — Alasan/dampak:** A keeps browsing smooth but requires a safe saved selection and return target; B is simpler but interrupts earlier. / A menjaga kelancaran browsing, dengan tambahan penyimpanan pilihan dan tujuan kembali; B lebih sederhana tetapi meminta login lebih awal. **F1 transactions ↔ F2 authentication.**

**Basis / Dasar:** R1 recommends signing in before purchase; R2 illustrates ticket selection and checkout. The exact return flow is our proposal. / R1 menyarankan login sebelum membeli; R2 mencontohkan pemilihan tiket dan checkout. Alur kembali yang persis adalah usulan proyek.

## 2. Discount combination / Gabungan diskon

- **A — Suggested / Disarankan:** Retain the F1 demo's event voucher + platform coupon + points, with server calculation and a zero floor. / Pertahankan kombinasi voucher event + kupon platform + poin pada demo F1; total dihitung server, minimum nol.
- **B:** One event voucher OR one platform coupon, plus points. / Salah satu voucher event ATAU kupon platform, ditambah poin.

**Why/impact — Alasan/dampak:** A preserves the existing F1 interaction; it needs more combination/restoration tests. B reduces combinations but changes the discount UI. / A mempertahankan interaksi F1 yang sudah ada, dengan tambahan tes kombinasi/pengembalian. B mengurangi kombinasi tetapi mengubah UI diskon. **F1 checkout/restoration ↔ F2 rewards/dashboard rejection.**

**Basis / Dasar:** PRD requires these reward types but leaves stacking unspecified. R3 supports promo-code entry, not a particular stacking rule. / PRD menyebut jenis reward tersebut, tetapi tidak mengatur penggabungannya. R3 mencontohkan input kode promo; tidak membuktikan aturan stacking tertentu.

If A is chosen, the proposed demo order is voucher percentage → fixed coupon → points, consuming only the amount needed. Rp25,000 coupon value remains a separate pending decision. / Jika A dipilih, urutan usulan demo: persentase voucher → kupon nominal → poin, hanya memakai yang diperlukan. Nilai kupon Rp25.000 masih keputusan terpisah yang terbuka.

## 3. Free / zero-payable registration / Event gratis atau tagihan nol

- **A — Suggested / Disarankan:** Skip payment proof; record a done/confirmed registration and include it in the attendee list. / Tanpa bukti bayar; buat registrasi done/terkonfirmasi dan tampilkan di daftar attendee.
- **B:** Skip payment proof but require organizer acceptance/rejection. / Tanpa bukti bayar tetapi tetap menunggu accept/reject organizer.

**Why/impact — Alasan/dampak:** A is smaller and avoids reviewing a payment that does not exist; B adds an approval queue. Both require a real order and capacity accounting. / A lebih sederhana karena tidak perlu memeriksa pembayaran yang tidak ada; B menambah antrean persetujuan. Keduanya tetap memiliki catatan pesanan dan perhitungan kapasitas. **F1 payment/status flow ↔ F2 approval, attendee list and email.**

If B is chosen, the proposed three-day clock for this no-proof case starts at registration. / Jika B dipilih, usulan awal hitung tiga hari khusus kasus tanpa bukti ini adalah saat registrasi.

**Basis / Dasar:** PRD allows free events. R4 documents free/no-payment orders; using our done status is our proposed mapping. / PRD mengizinkan event gratis. R4 mendokumentasikan pesanan tanpa pembayaran; pemetaan ke status done adalah usulan proyek.

## 4. Three-day decision clock / Awal hitung keputusan tiga hari

- **A — Suggested / Disarankan:** For paid orders, start after successful proof upload, entering the confirmation stage. / Untuk pesanan berbayar, mulai setelah bukti berhasil diunggah dan masuk tahap konfirmasi.
- **B:** Start at the original checkout. / Mulai sejak checkout awal.

**Why/impact — Alasan/dampak:** A gives the organizer the full review window; B reduces it by the customer's upload delay. The proposed duration is 72 hours. The two-hour upload deadline is unchanged. / A memberi waktu review penuh; B menguranginya selama customer belum upload. Durasi usulan adalah 72 jam. Batas upload dua jam tetap berlaku. **F1 expiry/jobs/status ↔ F2 dashboard/decision deadline.**

**Basis / Dasar:** The PRD sets three days but does not state the start precisely. R5 illustrates organizer order/status visibility only; it does not establish our deadlines. / PRD menetapkan tiga hari tetapi awal hitung belum rinci. R5 hanya acuan tampilan data/status organizer, bukan sumber deadline proyek.

## 5. Attendance evidence / Bukti kehadiran untuk review

- **A — Suggested / Disarankan:** Organizer manually marks attendance in the attendee list. / Organizer menandai hadir secara manual di daftar attendee.
- **B:** Organizer verifies a ticket code or QR check-in. / Organizer memverifikasi kode tiket atau check-in QR.

**Why/impact — Alasan/dampak:** A fits a small graded MVP; B needs ticket-code/verification or scanning work. A completed purchase plus an ended event alone does not verify attendance. / A lebih ringan untuk MVP tugas; B menambah kode tiket/verifikasi atau pemindaian. Pembelian selesai dan event berakhir saja belum membuktikan kehadiran. **F2 attendee records ↔ F1 review eligibility; F1 ratings ↔ F2 organizer profile.**

**Basis / Dasar:** R6 demonstrates manual computer check-in; R7 demonstrates app/QR check-in. / R6 mencontohkan check-in manual; R7 mencontohkan check-in aplikasi/QR.
